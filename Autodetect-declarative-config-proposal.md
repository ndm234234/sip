## 1. О чём документ и для кого

Рядом лежит документ `Autodetect-generic-hook-analysis.md`. Он утверждает: без
дополнительного C++-кода нынешний конфиг-движок `GeneralGeneric::AutodetectTool`
способен заменить autodetect только у 2 брендов из 17, а полностью — только
у одного (NicTech).

Этот документ отвечает на семь вопросов:

1. **Правда ли это?** Да, вывод верен; часть формулировок нужно уточнить —
  см. раздел 6.
2. **Можно ли обойти ограничение, оставаясь декларативным?** То есть без
  встраивания скриптового языка внутрь конфига. Да, можно — см. разделы 7–10.
3. **Что при этом теряется?** Три класса поведения не переводятся в декларацию
  в принципе — см. раздел 11.
4. **Даёт ли это что-то при внедрении ИИ?** Да, и это, возможно, более весомый
  аргумент, чем экономия C++-кода — см. раздел 12.
5. **Хватит ли предложенной схемы реальным вендорам?** По результатам сплошной
  проверки всех семнадцати драйверов: **11 описываются конфигом без единой
   строчки C++, 2 требуют провайдера, 1 покрывается в основной ветке, и 3
   остаются хуком** — см. разделы 13 и 15.5. Число хуков проверено по коду,
   число «11» — гипотеза о достаточности словаря, и предложение на ней не
   держится: там, где словаря не хватит, предусмотрен выход в код через
   провайдер значения — см. 8.8, 11.7 и 14.
6. **Это шаг к zero code?** Нет: autodetect — 2–7% кода драйвера, и предложение
  меняет не количество кода, а его размещение — «код один раз, данные на
   вендора». Замеры и разбор термина — в 11.8.
7. **Работает ли тот же подход за пределами autodetect** — на детекторах
  аналитики, событиях и настройках? Да, и почти без хуков: в Go-стеке нужный
   шов уже проведён — см. раздел 18.

**Для кого.** Документ рассчитан на читателя, который не работал с
autodetect-подсистемой. Разделы 2 и 3 объясняют базовые понятия; если вы уже
знаете, что такое device description JSON и `.rep`, начинайте с раздела 4.

**Статус.** Предложенная схема — proposal, кода нет. Всё, что описано в
разделах 3–6, проверено по исходникам (ссылки с номерами строк в разделе 19).

## 2. Глоссарий: что такое autodetect и зачем он нужен

**Устройство (device)** — камера, видеорегистратор (NVR/DVR), модуль
ввода-вывода. Всё, что подключается к AxxonOne через драйвер.

**Autodetect** — процедура, которая по IP-адресу и учётным данным выясняет,
что за устройство находится на том конце, и составляет его «паспорт»: сколько
у него видеоканалов, сколько потоков на канале, какие есть детекторы, есть ли
PTZ (поворотная головка), сколько тревожных входов и выходов, есть ли
встроенный архив на SD-карте. Пользователь в интерфейсе AxxonOne нажимает
«добавить устройство» — под этим и работает autodetect.

**Device description JSON** — результат autodetect. Строка JSON, которая
кладётся в поле `IpDeviceDescription::m_deviceDescription` и уходит на сервер.
AxxonOne по ней строит дерево объектов камеры: сколько видеоисточников
создать, какие детекторы предложить в интерфейсе, показывать ли панель PTZ.
Если в JSON чего-то нет — в интерфейсе этого не будет, даже если устройство
физически это умеет.

**Драйвер (Generic-драйвер)** — C++-библиотека под конкретный бренд, живущая
в `Drivers/<Brand>Generic/`. Внутри каждого есть свой класс autodetect
(`AutodetectTool` либо `Autodetect`), который делает запросы к устройству
по его фирменному HTTP API (CGI) и собирает device description JSON.

**Хук (hook)** — здесь: любой кусок C++-кода, который приходится писать
специально под бренд, потому что общий механизм этого не умеет. Задача,
ради которой всё затевается — сократить количество хуков.

**`.rep`-файл** — репозиторий описаний устройств (`Drivers/*/Ipint.*.rep`).
XML, где перечислены модели, кодеки, детекторы, их свойства, события и
визуальные элементы. Часть драйверов не выдумывает описание детектора в коде,
а берёт его из `.rep` (функция `ITV8::Utility::fillDetectorFromRepository`).

**Визуальный элемент (visual element)** — зона, линия или прямоугольник,
который пользователь рисует поверх кадра, настраивая детектор. В device
description JSON описывается блоком `visualElements` с полями `type`
(`rectangle` / `polyline`), `minCount`, `maxCount`.

**`GeneralGeneric`** — драйвер-заготовка (`Drivers/GeneralGeneric/`), у
которого autodetect не зашит в код, а читается из внешнего JSON-файла. Это и
есть «конфиг-движок», о котором идёт речь. Идея: описать поведение
autodetect данными, а не кодом, и тем самым перестать писать хуки.

## 3. Как устроен autodetect сегодня

### 3.1. Общая схема

```
AxxonOne
   │  «добавь устройство 10.0.0.5, логин/пароль»
   ▼
Драйвер бренда  ──HTTP GET/POST──►  Устройство (CGI API вендора)
   │            ◄──ответ XML/JSON/текст──
   │  разбор ответов, сборка описания
   ▼
IpDeviceDescription { m_brand, m_model, m_firmware, m_mac,
                      m_deviceDescription = "<device description JSON>" }
   │
   ▼
AxxonOne строит объекты камеры
```

Важная деталь: результат autodetect **кэшируется** сервером в колонке
`genericDeviceDescription2` для конкретной камеры. Обновление драйвера само по
себе описание не перечитывает — чтобы увидеть изменения, камеру надо добавить
заново или запустить повторный autodetect из интерфейса.

### 3.2. Что делает бренд-специфичный драйвер

Типичный `AutodetectTool` бренда — это 300–800 строк C++, где вперемешку:

- последовательность HTTP-запросов к CGI устройства;
- разбор ответов (у каждого вендора свой формат);
- арифметика и подсчёты (сложить два числа, посчитать элементы списка);
- ветвления (NVR это или камера, поддерживается ли аналитика);
- сборка JSON.

Пример из `Drivers/DahuaGeneric/src/AutodetectTool.cpp:392`: число потоков на
канале считается как `1 + MaxExtraStream` — один основной поток плюс
дополнительные, число которых устройство сообщает отдельным запросом.

## 4. Что именно умеет конфиг-движок GeneralGeneric

### 4.1. Формат конфига

Конфиг — JSON-файл, путь к нему берётся из свойства `configFile` в `.rep`
(`AutodetectTool.cpp:115-130`). Пример для Hanwha лежит в
`Drivers/GeneralGeneric/HanwhaDescr`. Структура:

```json
{
  "Hanwha": {
    "AutodetectTool": {
      "channelsNum": { "url": "...", "reqType": "GET",
                       "parserType": "xml", "KeyWord": "MaxChannel",
                       "resultType": "int" },
      "profilesNum":  { ... },
      "rayRelayNums": { "rayNums": { ... }, "relayNums": { ... } },
      "audioInNum":   { ... },
      "AudioOutNum":  { ... },
      "detectors":    { "MotionDetection": { ... }, ... },
      "telemetry":    { "Absolute.Pan": { ... }, ... },
      "telemetryLimits": { "MaxPreset": { ... } }
    }
  }
}
```

Единица описания — `AttributeRequest` (`ConfigParser.h:11-18`), пять полей:
`url`, `reqType` (GET/POST/PUT/DELETE), `parserType` (`xml`/`json`/`text`),
`KeyWord` (что искать в ответе), `resultType` (декоративное поле, см. 5.7).

Обязательны блоки `channelsNum`, `profilesNum`, `rayRelayNums`, `audioInNum`,
`AudioOutNum` (`ConfigParser.cpp:117-151`) — их отсутствие роняет разбор
конфига целиком. Блоки `detectors`, `telemetry` и остальные опциональны.

### 4.2. Как исполняется

`doAutodetect` (`AutodetectTool.cpp:502-569`) делает ровно следующее:

1. Читает конфиг, берёт **первую** запись бренда: `configFile.front()`
  (строка 526).
2. Вызывает шесть геттеров-скаляров: каналы, профили, лучи, реле, аудиовход,
  аудиовыход (строки 537-542). Каждый — один HTTP-запрос.
3. Перебирает `detectors`: по одному bool-запросу на детектор (строка 543,
  реализация 452-480).
4. Перебирает `telemetry`: по одному bool-запросу на флаг PTZ, плюс один
  int-запрос на `MaxPreset` (строка 544, реализация 482-500).
5. Собирает JSON функцией `buildDeviceDescriptionJson` (262-349).

Все запросы **синхронные и последовательные**. Для `HanwhaDescr` это ровно
30 обращений к камере подряд: 6 скаляров + 8 детекторов + 15 флагов PTZ +
1 `MaxPreset`.

### 4.3. Как извлекается значение

Извлечение — `extractByType` в `ParserHelpers.cpp:224-242`, три стратегии:


| `parserType` | Что делает                                                                                                                                                  | Строки             |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| `xml`        | сначала рекурсивно ищет элемент с атрибутом `name == KeyWord` и берёт его атрибут `value`; если не нашёл — трактует `KeyWord` как точечный путь boost ptree | `131-151`, `15-37` |
| `json`       | сначала точечный путь ptree; если не вышло — рекурсивный поиск ключа с таким именем на любой глубине                                                        | `153-176`, `39-52` |
| `text`       | построчно (разделители `\r`/`\n`), ищет строку вида `KeyWord = значение`, обрезает пробелы                                                                  | `178-222`          |


Результат всегда один — **строка**. Дальше она превращается либо в `int`
через `lexical_cast` (`AutodetectTool.cpp:366-382`), либо в `bool` по правилу
«`true` или `1` — истина» (`110-113`).

### 4.4. Что получается на выходе

`buildDeviceDescriptionJson` (`262-349`) собирает жёстко заданную структуру:

- `brand` — имя бренда, `model` — всегда `generic`, `firmware` — всегда `auto`
(строки 270-272);
- `videoSources` — `channelsNum` одинаковых каналов, в каждом `profilesNum`
потоков с именами `stream_0`, `stream_1`, … и списком транспортов
TCP/UDP/Multicast/RTSP-over-HTTP (283-300);
- `detectors` — одинаковый набор на каждом канале (299);
- `audioSources` — только счётчик (302-303);
- `audioDestinations` — **ровно один** элемент, всегда G.711 / 64000 / 8000 /
µ-law, независимо от `audioOutNum` (305-323);
- `ioDevices` — **ровно один** элемент с числом лучей и реле (325-333);
- `telemetries` — один элемент, флаги выводятся из bool-ов (335, 160-260);
- `settings` — свойства устройства из `.rep` (337-346).

Набор детекторов, которые движок вообще способен объявить, зафиксирован в
`detectorSpecs()` (`69-83`) — их ровно восемь: `AudioDetection`,
`MotionDetection`, `FaceDetection`, `FogDetection`, `ShockDetection`,
`Tampering`, `DefocusDetection`, `TemperatureChangeDetection`. Ключ конфига,
которого нет в этой таблице, молча игнорируется с предупреждением в лог
(`461-466`).

Набор флагов PTZ тоже фиксирован — 15 ключей вида `Absolute.Pan`,
`Continuous.Zoom`, `Relative.Iris`, `Preset`, `AreaZoom` (`36-50`), а скорости
и шаги захардкожены константами (`28-33`).

## 5. Ограничения и дефекты нынешнего движка

### 5.1. Одна проба — одно скалярное значение

Нет способа сложить два числа, посчитать элементы списка, взять подстроку,
применить регулярное выражение, проверить бит. Всё, что умеет движок, —
«сходи по URL, найди ключ, верни int или bool».

### 5.2. Детектор — это одно событие и ноль зон

`appendDetectors` (`132-152`) пишет ровно один элемент `events[0]`, ставит
`maxCount = 1` и одну настройку — группу детектора. **Блока `visualElements`
нет вообще.** Отсюда следствия:

- Любой детектор с зоной (IVS, IVA, VCA, пересечение линии, окна детектора
движения) описать невозможно.
- Мультисобытийный детектор невозможен. Это не косметика: правило
`.cursor/rules/cpp-generic-autodetect-event-consistency.mdc` требует, чтобы
набор событий в autodetect совпадал с тем, что детектор реально
вырабатывает в рантайме, иначе макросы и автоправила молча не срабатывают.

### 5.3. Детекторы одинаковы на всех каналах

Цикл по каналам (283-300) вызывает `appendDetectors` с одним и тем же
вектором. Для NVR, где на разных каналах висят разные камеры, это заведомо
неверно.

### 5.4. Модель и прошивка всегда фиктивны

`model = generic`, `firmware = auto` (271-272). MAC-адрес не публикуется
вообще. Драйверы, которые честно читают модель (IDIS, Milesight, Dahua),
воспроизвести нельзя в принципе.

### 5.5. Конфиг всегда берётся из первой записи

`configFile.front()` (строка 526) — имя бренда (`m_brand`, установленное в
`checkBrand`, строка 362) используется **только** для поля `brand` в выводе
(строка 557), но не для выбора ветки конфига. Мультибрендовый файл сейчас
нерабочий: какой бренд ни запроси, применятся настройки первого.

При этом функция выбора ветки уже написана — `parseConfigFileBranch`
(`ConfigParser.h:50`, реализация `ConfigParser.cpp:297-306`) — и просто
нигде не вызывается. Починка — одна строка.

### 5.6. Мёртвые секции конфига

`detectorLimits` и `embeddedDetectorsCheck` разбираются
(`ConfigParser.cpp:159-171`, поля в `ConfigParser.h:31-33`), но
`AutodetectTool` к ним не обращается ни разу. В `HanwhaDescr` они заполнены
(строки 106-135) — три запроса лимитов и проверка `eventstatus.cgi` — и не
делают ничего.

### 5.7. `resultType` ни на что не влияет

Тип определяется тем, в какой слот попал запрос: `channelsNum` всегда int,
детектор всегда bool. Поле `resultType` встречается ровно один раз — в тексте
сообщения об ошибке (`AutodetectTool.cpp:379`). Конфиг, объявивший
`"resultType": "text"`, будет молча обработан как int.

### 5.8. Ошибка неотличима от нуля

`requestAttributeAsInt` возвращает `0` и при сетевой ошибке, и при ненайденном
ключе, и при неразобранном значении (`366-382`). Ноль каналов превращается в
один канал, ноль профилей — в два потока (`280-281`). Значит камера
«определится» почти всегда, даже если конфиг полностью неверен, — просто
получится дефолтная камера 1×2. Это делает критерий «камера появилась в
AxxonOne» бесполезным для оценки: осмысленный критерий — совпадение топологии.

### 5.9. Лучи и реле в примере перепутаны

В `HanwhaDescr` `rayNums` читает `MaxAlarmOutput` (строка 20), а `relayNums` —
`MaxAlarmInput` (строка 27). Луч — это тревожный **вход**, реле — **выход**;
значения стоят наоборот.

### 5.10. Мелочи схемы

Ключ аудиовыхода назван `AudioOutNum` с заглавной буквы
(`ConfigParser.cpp:21`), в отличие от всех остальных camelCase-ключей.
Секция `rayRelayNums` обязательна даже для устройства без ввода-вывода.

### 5.11. Производительность

30 последовательных синхронных HTTP-запросов на один autodetect — это
секунды на локальной сети и десятки секунд на канале с задержкой. Никакого
переиспользования ответов нет: даже если пятнадцать флагов PTZ лежат в одном
документе, движок сходит за ним пятнадцать раз.

## 7. Предложение: декларативная схема без скриптов

### 7.1. Задача

Описать autodetect данными так, чтобы покрыть перечисленные механизмы
(арифметику, подсчёты, циклы, сессии, ветвления), **не вводя внутрь конфига
язык программирования**: ни выражений в строках, ни встроенного Lua/JS, ни
условных операторов.

### 7.2. Ключевая идея

Вместо «списка запросов с ключами» — **граф именованных шагов с замкнутым
словарём операторов**. Пользователь конфига никогда не пишет выражение; он
выбирает оператор из фиксированного списка и передаёт ему аргументы, часть
которых — ссылки на другие шаги.

Это тот же приём, что в GitHub Actions или Kubernetes: YAML выразителен, но
языком не является, потому что набор действий конечен и определён движком.

### 7.3. Три правила, которые удерживают схему от превращения в язык

**Правило 1. Никаких выражений в строках.**
Арифметика записывается оператором, а не формулой:

```yaml
# так — нельзя:
channelCount: "${local} + ${remote}"
# так — можно:
channelCount: {sum: [{ref: values.local}, {ref: values.remote}]}
```

Единственная допустимая подстановка — `${...}` внутрь URL, тела запроса,
заголовка или имени. Внутри подстановки не может быть вызовов и операций,
только имя значения.

**Правило 2. Никакого потока управления.**


| Вместо                        | Используется                                                                       |
| ----------------------------- | ---------------------------------------------------------------------------------- |
| цикла `for`                   | `for_each` над диапазоном или списком (comprehension)                              |
| `if / else`                   | список `variants`, каждый со своим предикатом `when`; первый подошедший выигрывает |
| `break`                       | декларативный терминатор `stop_when` у последовательности                          |
| ленивой инициализации вручную | пробы вычисляются лениво: та, на которую никто не сослался, не выполняется         |


Ленивость важна именно для ветвлений: в ветке «камера» запрос логина в NVR
просто никем не упомянут и в сеть не уходит. Ветвление получается бесплатно,
без единого `if`.

**Правило 3. Словарь замкнут.**
Около 35 операторов: ~10 экстракторов, ~15 трансформов, ~12 предикатов.
Чего нет в списке — выразить нельзя, и это осознанная плата. Взамен:

- конфиг проверяется JSON-схемой ещё до запуска;
- любая новая идиома вендора — это явное расширение движка, обсуждаемое на
ревью, а не самодеятельность в конфиге;
- поведение полностью воспроизводимо, а значит тестируемо (см. 16.2), в том
  числе автоматически, что отдельно важно для ИИ-ассистентов (см. раздел 12).

У замкнутости есть очевидный риск: словаря может не хватить, а расширять его
под каждого вендора — значит потерять смысл замыкания. Поэтому в схеме
предусмотрен штатный аварийный выход — **провайдер значения** (8.8): чистая
C++-функция, подключаемая по имени. Он не ломает ни одно из трёх правил
(в конфиге по-прежнему нет ни выражений, ни управляющих конструкций, только
имя) и не выводит участок из-под тестов. Почему шов проходит именно здесь —
11.7.

### 7.4. Модель исполнения

```
     ┌─────────────┐
     │  sessions   │  логин, выдающий значения (токен, cookie)
     └──────┬──────┘
            │ inject: заголовок / cookie / query-параметр
            ▼
     ┌─────────────┐
     │   probes    │  HTTP-запросы; ленивые, кэшируемые, дедуплицируемые,
     └──────┬──────┘  при необходимости размноженные через for_each
            │
            ▼
     ┌─────────────┐
     │   values    │  именованные значения: экстрактор + цепочка трансформов
     └──────┬──────┘
            │
            ▼
     ┌─────────────┐
     │  variants   │  выбор профиля устройства предикатом when
     └──────┬──────┘
            │
            ▼
     ┌─────────────┐
     │  topology   │  итоговое описание: каналы, детекторы, PTZ, IO, аудио
     └─────────────┘
```

Правила исполнения:

- проба выполняется не более одного раза за autodetect, результат кэшируется;
- две пробы с одинаковыми методом, URL и телом схлопываются в одну (это само
по себе снимает проблему 5.11 — пятнадцать флагов PTZ из одного документа
дадут один запрос вместо пятнадцати);
- значение, которое никто не использует в выбранном варианте, не вычисляется;
- отсутствие значения — ошибка, если явно не задан `default` (это чинит 5.8).

## 8. Словарь операторов

### 8.1. Транспорт и аутентификация

```yaml
transport:
  scheme: http          # http | https
  port: 80
  auth: digest          # none | basic | digest | session:<id> | provider:<name>
```

Про `provider:` см. раздел 14.

### 8.2. Проба (probe)


| Поле       | Смысл                                 |
| ---------- | ------------------------------------- |
| `id`       | имя, по которому на пробу ссылаются   |
| `method`   | `GET` / `POST` / `PUT` / `DELETE`     |
| `path`     | URL, допускает подстановку `${...}`   |
| `body`     | тело запроса, допускает подстановку   |
| `headers`  | дополнительные заголовки              |
| `format`   | `xml` / `json` / `text` / `raw`       |
| `for_each` | размножение пробы (см. 8.6)           |
| `optional` | `true` — неуспех не считается ошибкой |


### 8.3. Экстракторы — откуда берётся значение


| Оператор                                                    | Что делает                                                                         |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `xml: {path: ..., attr: ...}`                               | точечный путь или атрибут XML-узла                                                 |
| `json: {path: "a.b[*].c"}`                                  | путь в JSON, поддерживает `[*]`                                                    |
| `kv: {key: ..., pair_sep: ..., kv_sep: ..., unquote: true}` | разбор `ключ=значение`; разделители задаются (`\n` для CRLF-формата, `&` для IDIS) |
| `kv: {key_matches: "<regex>"}`                              | то же, но ключи отбираются регуляркой                                              |
| `regex: {pattern: ..., group: N}`                           | значение из группы регулярного выражения                                           |
| `header: {name: ...}`                                       | заголовок HTTP-ответа                                                              |
| `status: {}`                                                | код ответа                                                                         |
| `const: <значение>`                                         | литерал                                                                            |
| `repository: {path: ...}`                                   | значение из `.rep`                                                                 |


### 8.4. Режим кардинальности — сколько значений вернуть

Приписывается к любому экстрактору полем `mode`:


| Режим                        | Результат                                 | Кому нужен                                                                  |
| ---------------------------- | ----------------------------------------- | --------------------------------------------------------------------------- |
| `first` (по умолчанию)       | первое совпадение                         | всем                                                                        |
| `all`                        | список совпадений                         | Axis, Uniview                                                               |
| `count`                      | количество совпадений                     | Hikvision, Senturian, Panasonic, Axis                                       |
| `exists`                     | `true`, если ключ вообще присутствует     | Vivotek (детектор движения определяется наличием ключа, а не его значением) |
| `count_distinct: {group: N}` | число различных значений группы регулярки | Dahua (число зон детектора)                                                 |


### 8.5. Трансформы — цепочка преобразований значения

`as` (int/bool/string), `add`, `sub`, `mul`, `div`, `sum`, `min`, `max`,
`clamp`, `default`, `bit_and`, `bit_test`, `map`, `prefix_map`, `oui_map`,
`trim`, `unquote`, `split`, `join`, `length`, `unique`, `filter`, `first_of`.

Два из них заслуживают пояснения:

- **`first_of`** — упорядоченный список источников; побеждает первый, который
  вообще дал значение. Это штатный способ описать «сначала попробуй так, если
  не вышло — эдак» (Axis: PTZ регуляркой, иначе через параметры оптики).
- **`map` / `prefix_map` / `oui_map`** — таблицы соответствия вместо кода:
  значение → идентификатор, префикс модели → бренд, OUI MAC-адреса → бренд.

### 8.6. Итерация

```yaml
# по диапазону, граница берётся из другого значения
for_each: {range: {from: 1, to_ref: values.channelCount}}

# по элементам списка
for_each: {ref: values.acapList}

# по последовательности неизвестной длины, с декларативным терминатором
for_each: {sequence: {from: 1, max: 64, stop_when: {status: {ne: 200}}}}
```

Внутри доступны подстановки `${item}` (текущий элемент или индекс) и
`${index}` (порядковый номер).

### 8.7. Предикаты

`eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `contains`, `starts_with`,
`matches`, `exists`, `bit_test`, и комбинаторы `all_of`, `any_of`, `not`.

Предикат — всегда структура, не строка:

```yaml
when: {all_of: [{ref: values.pan, exists: true},
                {ref: values.tilt, exists: true}]}
```

### 8.8. Провайдер значения — аварийный выход в код

Словарь операторов конечен, и рано или поздно встретится вендор, чьё значение
им не выражается. Чтобы это не превращалось в «застряли посреди перехода»,
в схеме есть штатный аварийный выход: **именованная чистая функция**,
реализованная в C++ и подключаемая по имени.

```yaml
values:
  # обычный путь — операторы
  channelCount: {sum: [{ref: values.local}, {ref: values.remote}]}

  # аварийный выход — провайдер значения
  motionZoneCount:
    provider: dahua_motion_window_count      # (payload, params) -> int | list
    input: {probe: motionCfg, params: {channel: "${item}"}}
```

Это прямой аналог `useMemo` в React: именованное производное значение,
вычисляемое обычным кодом, при том что описание результата остаётся
декларативным. Обоснование такого шва — 11.7.

**Контракт провайдера (обязателен, иначе теряется весь смысл затеи):**

| Требование | Почему |
|---|---|
| чистая функция от тела ответа и параметров | иначе golden-тест перестаёт покрывать этот участок |
| нет обращений к сети | пробы делает только движок — иначе рушится ленивость и дедупликация |
| нет состояния между вызовами и обращений ко времени | иначе результат невоспроизводим |
| возвращает скаляр или список, не кусок итогового JSON | топология остаётся декларативной целиком |

При соблюдении контракта замена оператора на провайдер **не выводит участок
из-под теста**: движок по-прежнему прогоняется на фикстурах и сравнивается с
эталоном. Это ключевое отличие провайдера значения от хука.

**Бюджет.** Провайдер — не бесплатный. Ориентир для ревью: не более двух-трёх
провайдеров значения на вендора. Больше — признак, что вендор на самом деле
хук (раздел 15), и честнее назвать вещи своими именами. Провайдер,
понадобившийся второму вендору, — кандидат в операторы словаря; так словарь
растёт из практики, а не из предугадывания.

## 9. Полная схема конфига

Ниже полный скелет с комментариями. Пример собирательный: он показывает форму,
а не реальную конфигурацию конкретной камеры.

```yaml
version: 1
brand: Hikvision                 # явный ключ бренда — чинит дефект 5.5

transport:
  scheme: http
  port: 80
  auth: session:isapi

# ─── Сессии: те же примитивы, что и пробы, просто с инъекцией результата ───
sessions:
  - id: isapi
    steps:
      - id: caps
        method: GET
        path: /ISAPI/Security/sessionLogin/capabilities
        extract:
          salt: {xml: {path: SessionLoginCap.salt}}
      - id: login
        method: POST
        path: /ISAPI/Security/sessionLogin
        body:
          template: "<SessionLogin><password>${values.pwHash}</password></SessionLogin>"
        extract:
          cookie: {header: {name: Set-Cookie}, regex: {pattern: "(WebSession=[^;]+)"}}
    inject:
      - {header: {name: Cookie, value: "${cookie}"}}
    logout: {method: PUT, path: /ISAPI/Security/sessionLogout}

# ─── Пробы: ленивые, кэшируемые, дедуплицируемые ──────────────────────────
probes:
  - {id: caps,  method: GET, path: /ISAPI/System/capabilities, format: xml}
  - {id: chans, method: GET, path: /ISAPI/System/Video/inputs/channels, format: xml}
  - id: profiles                                     # проба на каждый канал
    for_each: {range: {from: 1, to_ref: values.channelCount}}
    method: GET
    path: /ISAPI/Streaming/channels?channelId=${item}
    format: xml
    optional: true

# ─── Значения: экстрактор + трансформы ────────────────────────────────────
values:
  channelCount:
    first_of:                                        # приоритетный список
      - {probe: chans, xml: {path: VideoInputChannelList.VideoInputChannel}, mode: count}
      - {probe: caps,  xml: {path: DeviceCap.RacmCap.inputProxyNums}, as: int}
      - {const: 1}

  streamsPerChannel:                                 # список, индексируемый каналом
    for_each: {range: {from: 1, to_ref: values.channelCount}}
    select: {probe: "profiles[${item}]",
             xml: {path: StreamingChannelList.StreamingChannel}, mode: count}
    default: 2

  model: {probe: caps, xml: {path: DeviceInfo.model}, trim: true}
  fw:    {probe: caps, xml: {path: DeviceInfo.firmwareVersion}}
  mac:   {probe: caps, xml: {path: DeviceInfo.macAddress}}

  motionZones:                                       # аварийный выход, см. 8.8
    provider: hikvision_motion_grid_count
    input: {probe: caps}

# ─── Варианты: взаимоисключающие профили, побеждает первый подошедший ─────
variants:
  - id: nvr
    when: {ref: values.channelCount, gt: 1}
    topology: {…}                                    # можно переопределить всё
  - id: camera
    default: true
    topology: {…}

# ─── Топология: полное описание, а не фиксированный набор слотов ──────────
topology:
  identity:
    model: {ref: values.model}                       # чинит дефект 5.4
    firmware: {ref: values.fw}
    mac: {ref: values.mac}
    brand:
      first_of:
        - {oui_map:    {ref: values.mac,   table: {"00:11:22": RVi}}}
        - {prefix_map: {ref: values.model, table: {NP: Novicam, GD: Gazer}}}
        - {const: Hikvision}

  video_sources:
    for_each: {range: {from: 1, to_ref: values.channelCount}}
    id: "${item}"
    name: {ref: "values.channelNames[${item}]", default: {template: "Channel ${item}"}}
    streams: {ref: "values.streamsPerChannel[${item}]"}

    detectors:                                       # чинит дефекты 5.2 и 5.3
      - id: motionDetection
        when: {ref: "values.motionEnabled[${item}]", eq: true}
        group: MotionDetection
        events:                                      # список, а не одно событие
          - {id: motionDetection, type: twoPhase}
        visual_elements:
          - {id: motionDetectionRule, type: rectangle,
             min: 1, max_ref: "values.motionZoneCount[${item}]"}
        properties_from_repository: true             # свойства берутся из .rep
      - from_repository:                             # детекторы, найденные динамически
          ids_ref: values.supportedVca

  telemetry:
    for_each: {range: {from: 1, to_ref: values.channelCount}}
    continuous_move: {when: {all_of: [{ref: values.panSpeedMax, exists: true},
                                      {ref: values.tiltSpeedMax, exists: true}]}}
```

## 10. Рецепты для трудных случаев

Ниже — по одному механизму, который сегодня требует хука. У каждого рецепта
одна и та же форма: **было** (фрагмент императивного C++) → **стало**
(эквивалент в декларативном конфиге). В скобках — драйвер, из-за которого
механизм понадобился. Ссылки на строки — на исходники репозитория.

Часть рецептов выглядит **длиннее** исходного C++. Это ожидаемо и разобрано
отдельно в 10.18 — прочитайте эту оговорку до того, как использовать длину
как аргумент за или против схемы.

### 10.18. Оговорка: почему часть деклараций длиннее кода

Возражение «в C++ это одна строка, а в YAML пять» звучит на каждом обсуждении
и заслуживает прямого ответа, а не отговорки «зато декларативно».

**Чаще всего сравниваются разные уровни.** Строка

```cpp
exposureEvents.find("VideoBlind") != std::string::npos
```

действительно короче рецепта 10.10, но она не работает сама по себе: рядом в
драйвере живут HTTP-запрос за `exposureEvents`, разбор ответа, обработка
ошибки, сборка `Json::Value` и цикл по каналам. В конфиге видно только
намерение, а перечисленное лежит в движке и пишется один раз на все семнадцать
вендоров. Честное сравнение — не «строка против строки», а весь `doAutodetect`
вендора против всего его конфига.

**Там, где декларация длиннее по существу, длина — это явность.** Рецепты 10.8
(`stop_when`), 10.16 (`variants`) и 10.17 (`sessions`) выписывают то, что в
C++ держится на соглашениях и знании локальных хелперов: «перебирай, пока ключ
есть», «сначала проверь, не NVR ли это», «после логина клади токен в заголовок».
Читатель конфига видит это, не открывая соседние файлы.

**Длину полезно использовать как метрику здоровья словаря**, а не как цель:

| Что наблюдаем | Как читать |
|---|---|
| YAML немного длиннее, но без циклов и состояния | норма, плата за единый движок и тесты |
| одна и та же громоздкая конструкция повторяется у нескольких вендоров | кандидат в новый оператор — схлопнуть шаблон |
| конфиг раздувает ровно один вендор | провайдер значения (8.8), а не расширение словаря |
| конфиг и длиннее, и **непонятнее** исходного C++ | плохой перевод; переделать или оставить код |

Критерий ревью формулируется так: **быстрее ли понять намерение, чем по C++**,
а не «меньше ли символов». Первое — то, ради чего затевается схема; второе —
побочный эффект, который случается не всегда.

**И честная граница.** Выигрыш предложения (golden-тесты без камеры, замкнутый
цикл для ИИ, один разбор HTTP на всех, явные границы «оператор / провайдер /
хук») не зависит от количества строк. Если конкретный шаг после перевода стал
длиннее и при этом не даёт ни одного из этих эффектов — его не нужно защищать
ссылкой на декларативность: там уместнее маленький провайдер или код.

## 11. Границы перевода: что императивно и остаётся таким

Раздел 10 показывает, что подавляющее большинство императивного кода в
autodetect переводится в декларацию механически. Здесь объясняется, **почему**
это так и **где** перевод заканчивается. Раздел важен для ревью: он даёт
критерий, по которому видно, что очередной вендор за границей схемы, — до
того как на него потрачена неделя.

### 11.1. Почему перевод вообще возможен

Императивный код в autodetect почти всегда описывает **как** получить число,
а конфиг описывает, **какое** число нужно. Пока «как» — это чистая функция от
ответа устройства (нет побочных эффектов, нет состояния, переживающего вызов,
результат зависит только от входных байтов), перевод механический.

Возьмём самый наглядный случай — подсчёт зон детектора у Dahua (рецепт 10.13
уже показывает пару «было / стало»). Что исчезло при переводе и почему это
не потеря:


| Было в C++                           | Куда делось                                                                                  |
| ------------------------------------ | -------------------------------------------------------------------------------------------- |
| цикл `for (int i = 0; i < 100; ++i)` | растворился в намерении «посчитай различные»                                                 |
| изменяемый счётчик `count`           | стал именованным значением, вычисляемым один раз                                             |
| `break` при первой дырке             | стал свойством оператора, а не отдельной инструкцией                                         |
| верхняя граница `100`                | исчезла: она существовала только потому, что программисту нужно было чем-то ограничить `for` |
| комментарий «обычно меньше 100»      | исчез вместе с границей                                                                      |


Последняя строка таблицы — самое интересное. Ограничение в сто итераций не
является свойством устройства; это артефакт того, что автор писал цикл.
Декларация не воспроизводит артефакты реализации, поэтому она короче не
только визуально, но и по объёму описываемого поведения.

### 11.2. Таблица соответствий: императивная конструкция → декларативная


| Императивная конструкция                  | Декларативный аналог                     | Пример      |
| ----------------------------------------- | ---------------------------------------- | ----------- |
| `for` по фиксированному диапазону         | `for_each: {range: {...}}`               | 10.12       |
| `for` по элементам списка                 | `for_each: {ref: ...}`                   | 10.14       |
| `while (ключ существует)`                 | `for_each: {sequence: {stop_when: ...}}` | 10.8        |
| счётчик `++count` в цикле                 | `mode: count`                            | 10.3        |
| счётчик по уникальным значениям           | `mode: {count_distinct: {group: N}}`     | 10.13       |
| `break`                                   | `stop_when` либо семантика самого `mode` | 10.8, 10.13 |
| `if / else` на уровне устройства          | `variants` + `when`                      | 10.16       |
| `if` на уровне отдельного элемента        | поле `when` у элемента топологии         | 9           |
| несколько связанных условий               | `when: {all_of: [...]}`                  | 9, 10.9     |
| `a + b`, `1 + x`                          | `sum`, `add`                             | 10.1, 10.2  |
| побитовая проверка `x & 0b100`            | `bit_test`                               | 10.9        |
| `str.find(...) != npos`                   | `regex` + `mode: exists` либо `contains` | 10.10       |
| `map.find(key)` с таблицей соответствий   | `map`, `prefix_map`, `oui_map`           | 9, 10.14    |
| «сначала так, если не вышло — эдак»       | `first_of`                               | 9, 10.3     |
| `try { lexical_cast } catch { default }`  | `as: int` + `default`                    | 10.2        |
| временная переменная, используемая дважды | именованное значение в `values`          | везде       |
| рекурсивный поиск ключа в дереве          | встроен в экстракторы `json` / `xml`     | 8.3         |
| регулярка с побочным действием            | `mode: all` + `unique`                   | см. ниже    |


Последняя строка заслуживает пояснения, потому что выглядит как явный
кандидат в «непереводимые». В `Drivers/DahuaGeneric/src/AutodetectTool.cpp:544-551`
используется `boost::xpressive` с семантическим действием: регулярное
выражение при каждом совпадении вставляет захваченную группу в `std::set`, а
цикл по итератору написан пустым — он существует только чтобы прогнать
побочный эффект.

```cpp
const bx::sregex SUPPORTED_RULES_RE = bx::as_xpr("caps.SupportedScenes.") >> plan
    >> bx::as_xpr(".SupportedRules.") >> (bx::s1 = +bx::_w) >> bx::as_xpr(".") >> -+bx::_ >> bx::_ln
    [bx::ref(rules)->*bx::insert(bx::as<std::string>(bx::s1))];

bx::sregex_iterator supportedRulesIt(vaCaps.begin(), vaCaps.end(), SUPPORTED_RULES_RE);
bx::sregex_iterator supportedRulesEnd;
while (supportedRulesIt != supportedRulesEnd)
    ++supportedRulesIt;
```

Побочный эффект здесь мнимый: намерение автора — «собрать множество
уникальных имён правил». Декларативно это две операции:

```yaml
rulesByScene:
  select: {probe: vaCaps,
           regex: {pattern: "caps\\.SupportedScenes\\.${item}\\.SupportedRules\\.(\\w+)\\.", group: 1},
           mode: all}
  unique: true
```

Мораль: наличие мутации в коде ещё не означает, что поведение императивно.
Прежде чем объявлять случай непереводимым, стоит спросить, что именно автор
хотел получить, а не как он это сделал.

### 11.3. Граница 1: порядок выполнения и побочные эффекты

**Что не выражается.** Сценарий «сначала измени что-то на устройстве, потом
прочитай результат». Например: включить детектор через `setConfig`, затем
прочитать его параметры, затем выключить обратно.

**Почему.** Модель исполнения из 7.4 намеренно лишает конфиг контроля над
порядком: пробы ленивые, кэшируемые и дедуплицируемые, движок вправе
переставить их местами, выполнить параллельно или не выполнить вовсе.
Именно это даёт бесплатное ветвление и схлопывание пятнадцати запросов PTZ в
один. Порядок и кэширование несовместимы: как только проба меняет состояние
устройства, её нельзя ни переиспользовать, ни пропустить.

**Насколько это больно.** Не больно: autodetect по определению не должен
менять конфигурацию устройства. Из семнадцати проверенных драйверов ни один
этого не делает в autodetect (в рантайме — сколько угодно). Так что граница
проходит там, где и должна.

**Единственное упорядоченное место в схеме** — шаги внутри сессии
(`sessions[].steps`). Они выполняются строго по порядку, потому что логин
принципиально последователен: получить соль, посчитать хэш, отправить,
забрать cookie. Это исключение сделано осознанно и ограничено логином.

**Что делать, если вендор всё-таки требует.** Не расширять `probes`
упорядоченностью — это уничтожит модель. Провайдер значения здесь тоже не
поможет: он не ходит в сеть по определению (8.8). Остаётся честный хук
(раздел 15). Признак, по которому это распознаётся на
ревью: в коде драйвера встречается `setConfig` / `PUT` / `POST` с телом
настройки **внутри** autodetect.

### 11.4. Граница 2: ранний выход со смыслом «это не то устройство»

**Что не выражается сейчас.** Различие между тремя разными исходами:

1. значение не пришло, но это нормально — подставить умолчание;
2. значение не пришло, и это ошибка обнаружения — прервать autodetect;
3. значение пришло, но оно доказывает, что на том конце **устройство другого
  вендора** — прервать autodetect с ясным диагнозом.

В предложенной схеме есть только `default`, то есть первый исход. Второй
описывается неявно (нет `default` — значит ошибка), третий не описывается
никак.

**Откуда это взялось.** `NicTechGeneric` бросает исключение при нулевом числе
каналов, и это осмысленно: у настоящего NicTech каналов не бывает ноль,
значит ответ пришёл не от NicTech. Нынешний движок `GeneralGeneric` этот
случай проглатывает и выдаёт камеру 1×2 (дефект 5.8) — то есть подтверждает
чужое устройство как своё.

**Чего не хватает в схеме.** Отдельного поля `assert`, отличающего «чужое
устройство» от «наше устройство без этой возможности»:

```yaml
values:
  channelCount:
    select: {probe: devability, xml: {path: response.devability.vin}, as: int}
    assert:
      when: {gt: 0}
      else: foreign_device        # foreign_device | detect_error
      message: "vin=0: устройство не NicTech"
```

Семантика трёх значений:


| Поведение                        | Когда применять                       | Что получит AxxonOne                               |
| -------------------------------- | ------------------------------------- | -------------------------------------------------- |
| `default: N`                     | возможности нет, но устройство наше   | описание без этой возможности                      |
| отсутствие `default`             | значение обязательно, ответа нет      | ошибка обнаружения                                 |
| `assert: {else: foreign_device}` | ответ доказывает чужую принадлежность | «устройство не распознано», без ложного добавления |


**Статус.** Это пробел в предложении, а не граница возможностей: `assert`
описывается декларативно и должен быть в словаре (раздел 8). Он вынесен сюда,
потому что обнаружился при разборе именно этой границы.

### 11.5. Граница 3: состояние, переживающее autodetect

**Что не выражается.** Ситуация, когда autodetect создаёт живой объект —
сокет, сессию, таймер — которым потом пользуется драйвер в рантайме.

**Пример.** `LuminysGeneric` в режиме авторегистрации
(`Drivers/LuminysGeneric/src/AutodetectTool.cpp:16-50`) поднимает слушающий
сокет на TCP-порту 60005, дожидается входящего соединения **от устройства**,
разбирает его идентификатор, проводит рукопожатие, получает токен и запускает
таймер поддержания соединения. Тот же сокет и тот же токен затем используются
классом `Device` в рантайме
(`Drivers/LuminysGeneric/src/ModuleDriver.cpp:211-237`).

**Почему это принципиально.** Конфиг описывает **результат** обнаружения —
структуру устройства. Он не описывает объекты и их время жизни. Как только
результатом становится «вот вам живой сокет», декларация теряет смысл: её
нечем выразить и нечем протестировать (в golden-тесте нет живого сокета).

**Смежный, но переводимый случай.** Сессия, которую можно установить заново.
Vivotek NVR и Hikvision логинятся в autodetect, но их логин идемпотентен и
дёшев: рантайм спокойно логинится повторно. Такие сессии описываются
декларативно (раздел 8.1) и переиспользования не требуют:

```yaml
sessions:
  - id: isapi
    reuse_in_runtime: false      # рантайм логинится сам, autodetect за собой убирает
    logout: {method: PUT, path: /ISAPI/Security/sessionLogout}
```

Разница между Luminys и Vivotek — не в наличии сессии, а в том, кто кому
звонит. Пока соединение инициируем мы, сессию можно установить заново.
Как только соединение инициирует устройство, повторить его по требованию
нельзя, и объект приходится хранить.

### 11.6. Чек-лист ревьюера: вендор за границей схемы?

Ответ «да» хотя бы на один вопрос из первых семи означает, что чистой
декларацией не обойтись — нужен провайдер (раздел 14) или хук (раздел 15).
Последний вопрос — исключение: он границей не является.

- [ ] Есть ли в autodetect запрос, **меняющий** конфигурацию устройства (`setConfig`, `PUT`/`POST` с настройками)? → граница 11.3.
- [ ] Зависит ли результат запроса от того, какой запрос был сделан **до** него (кроме шагов логина)? → граница 11.3.
- [ ] Создаёт ли autodetect объект, который используется **после** его завершения (сокет, подписка, таймер)? → граница 11.5.
- [ ] Инициирует ли соединение **устройство**, а не мы? → граница 11.5, случай Luminys.
- [ ] Используется ли транспорт, отличный от HTTP и SOAP (SIP, gRPC, проприетарный SDK)? → раздел 15.
- [ ] Приходит ли ответ **не документом** — C-структурами или байтами со смещениями вместо XML/JSON/`key=value`/текста? → раздел 15, случай Honeywell.
- [ ] Требуется ли криптографическое преобразование, специфичное для одного вендора? → провайдер аутентификации, раздел 14.
- [ ] Не хватает оператора для вычисления значения, хотя данные в ответе есть? → это **не** граница: провайдер значения, 8.8.

Если все ответы «нет», вендор описывается конфигом; остаётся проверить, что
хватает операторов из раздела 8, а где не хватает — провайдера значения (8.8).

### 11.7. Где должен проходить шов: урок React

Разделы 11.3–11.5 очертили границы схемы. Здесь — вывод из них: **где именно
проводить черту между декларацией и кодом**, и почему выбранное место не
случайно.

Самая известная реализация этой идеи — React, и на него естественно ссылаться
в обсуждении. Ссылаться нужно аккуратно, потому что расхожая формулировка
«React декларативен без языка» неверна и в споре обернётся против
предложения. React встроен в JavaScript: цикл — это `.map()`, условие —
тернарник, вычисление данных — произвольный код. Декларативно там **дерево,
которое компонент возвращает**, а не то, что его вычисляет.

Отсюда таблица, которая и объясняет выбор шва:

| | Цель: что должно получиться | Вывод: как получить данные |
|---|---|---|
| React | декларативно (JSX) | императивно (JavaScript) |
| Нынешние C++-драйверы | императивно (сборка `Json::Value` вручную) | императивно |
| `GeneralGeneric` сегодня | декларативно, но форма жёстко зашита | декларативно и крайне бедно (скаляр из одной пробы) |
| Предложение | декларативно (`topology`) | декларативно (операторы), с выходом в код через провайдер (8.8) |

Что из этого следует практически.

**Декларативность цели бесспорна и даёт основную пользу.** Именно она делает
результат воспроизводимым, сравнимым с эталоном и проверяемым схемой. Именно
на ней держатся golden-тесты (16.2) и весь выигрыш для ИИ-ассистентов
(раздел 12). Эту часть стоит защищать твёрдо.

**Декларативность вывода — гипотеза, а не догма.** Утверждение «35 операторов
покрывают всю HTTP-логику семнадцати драйверов» проверяемо (раздел 13), но
верить в него заранее никто не обязан. Поэтому предложение построено так,
чтобы **не зависеть** от истинности этой гипотезы: там, где оператора не
хватило, пишется провайдер значения на двадцать строк, а не хук на шестьсот.

Это снимает главное практическое возражение — «застрянем посреди перехода».
Свойства «всё или ничего» у схемы нет: цена ошибки в оценке словаря равна
одной небольшой функции, а не остановке работы над вендором.

**Тот же шов в репозитории уже есть.** В Go-стеке брендовый код не ходит в
камеру — он возвращает `RequestDescription` (url, метод, заголовки, тело),
а исполняет запрос C++-хост
(`Go/GrpcServer/helpers/grpc/builders/primitives/requestDescription.go`).
Разделение «что запросить — данные» и «кто исполняет — движок» команда уже
приняла и эксплуатирует. Предложение продолжает ту же линию на один шаг:
декларативно описывается не только запрос, но и то, что делать с ответом.
Второй существующий прецедент — сами `.rep`-файлы: возможности устройства
(кодеки, детекторы, свойства, визуальные элементы) уже описываются данными,
и никто не пишет под них C++.

### 11.8. Масштаб: это шаг к zero code?

Вопрос возникает сразу после слов «драйвер без C++», и отвечать на него надо
цифрой, иначе предложению припишут обещание, которого оно не давало.

**Autodetect — это 2–7% кода драйвера.** Замер по строкам `.cpp`/`.h` в
`Drivers/<Brand>Generic/src/`:

| Драйвер | Всего строк | Из них autodetect | Доля |
|---|---:|---:|---:|
| DahuaGeneric | 10 202 | 691 | 6.8% |
| MilesightGeneric | 10 971 | 516 | 4.7% |
| HanwhaGeneric | 21 147 | 750 | 3.5% |
| VivotekGeneric | 14 052 | 354 | 2.5% |
| HikvisionGeneric | 22 843 | 531 | 2.3% |

Даже полный успех схемы убирает только эту долю. Всё остальное — рантайм:
стриминг, PTZ, `applySettings`, разбор событий, детекторы, переподключения.
«Драйвера без кода» из предложения не следует, и обещать его не нужно.

**Код не исчезает, а переезжает.** Сегодня разбор HTTP-ответов написан
семнадцать раз в семнадцати драйверах; после перехода он написан один раз в
движке, а на вендора остаются данные. Правильная формула — не zero code, а
**«код один раз, данные на вендора»**. Ценность не в 2–7% на драйвер, а в том,
что эти проценты перестают дублироваться и начинают тестироваться
централизованно (16.2).

**Аудитория не та, что подразумевает zero-code-риторика.** Конфиг пишет не
заказчик и не менеджер, а интегратор, читающий вендорскую документацию в
Lexiro. Это low-code для инженера, а не zero-code для пользователя.

**Что было бы настоящим «брендом без кода».** Декларативный рантайм: применение
настроек, разбор потока событий, PTZ, переподключения. Раздел 18 показывает,
что бо́льшая часть этого действительно описывается тем же словарём — в Go-стеке
обработчики уже возвращают описания запросов, а не выполняют их. Но
непереводимое там тоже есть, и оно того же рода, что в границах 11.3–11.5:
удержание соединения, реконнект, двухфазный автомат события, время. Эти вещи
остаются в движке. Поэтому даже полное расширение схемы даёт не «ноль кода», а
«код один раз в движке» — просто с гораздо большей долей вендорской специфики,
переехавшей в данные.

**Почему термин лучше не использовать.** Если целью объявить отсутствие кода,
схема поедет в inner-platform effect: в конфиг добавят выражения, потом
условия, потом переменные — и получится плохой язык программирования внутри
YAML. Ровно от этого защищают три правила раздела 7, провайдеры как аварийный
выход (8.8, 14) и бюджет на них.

**Что меняет ИИ.** Ассистент одинаково легко порождает и C++, и YAML, поэтому
ценность не в отсутствии кода, а в проверяемости результата (раздел 12).
Ближайшая честная формулировка выигрыша — не «zero code», а «zero циклов
ручной проверки на стенде».

## 12. Схема и ИИ: почему декларативность меняет экономику

Раздел отвечает на вопрос, полезен ли предложенный подход при внедрении
ИИ-ассистентов в интеграцию камер. Короткий ответ: да, и выигрыш здесь, по
всей видимости, больше, чем от экономии C++-кода как такового. Причина не в
том, что «YAML проще генерировать», а в том, что меняется структура задачи.

### 12.1. Проблема сегодня: цикл проверки разомкнут

Сейчас агент, интегрирующий новый бренд, пишет 400–800 строк C++ и
**не может себя проверить**. Единственный способ узнать, верен ли autodetect,
— живая камера на стенде. Отсюда цепочка:

```
агент пишет код ──► компиляция (ловит только синтаксис)
                     │
                     ▼
                  ревью человеком (ловит часть логики)
                     │
                     ▼
                  стенд с камерой (ловит остальное) ──► итерация: часы или дни
```

Практическое следствие: агент выдаёт правдоподобно выглядящий код и
останавливается, потому что дальше проверять нечем. Ошибка обнаруживается на
ревью или у заказчика. Именно поэтому вокруг этой работы наросло столько
текстовых правил (`cpp-generic-driver-pitfalls-*`,
`cpp-generic-autodetect-event-consistency`) — они заменяют отсутствующую
автоматическую проверку человеческой дисциплиной.

### 12.2. Что меняет схема: цикл замыкается

Детерминированный движок плюс фикстуры дают проверку без камеры:

```
агент пишет конфиг ──► JSON-схема       (словарь, обязательные поля)  секунды
                        │
                        ▼
                       валидатор графа  (ссылки, циклы, недостижимость) секунды
                        │
                        ▼
                       golden-тест      (семантика на записанных ответах) секунды
                        │
                        ▼
                       расхождение → агент правит сам ──► итерация: секунды
```

Три уровня фильтра ловят разное:


| Уровень         | Что ловит                                                                  | Пример ошибки                                          | Когда срабатывает       |
| --------------- | -------------------------------------------------------------------------- | ------------------------------------------------------ | ----------------------- |
| JSON-схема      | несуществующий оператор, опечатку в поле, неверный тип                     | `mode: cont` вместо `count`                            | до запуска              |
| валидатор графа | ссылку на несуществующее значение, цикл в зависимостях, недостижимую пробу | `to_ref: values.chanCount` при значении `channelCount` | до запуска              |
| golden-тест     | неверный URL, не тот ключ, ошибку в арифметике, потерянный детектор        | посчитал 2 потока вместо 3                             | за секунды на фикстурах |


Ключевое здесь — третий уровень. Первые два ловят форму, и их можно получить
и без всей затеи. Именно golden-тест превращает «сгенерировал и надеюсь» в
«сгенерировал, проверил, поправил» — то есть в режим, где модели работают
принципиально лучше.

### 12.3. Пространство вывода сжимается на порядок


|                             | Сейчас (C++)                                                                                                     | Со схемой (YAML)                          |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| Объём на бренд              | 400–800 строк                                                                                                    | 60–100 строк                              |
| Возможных ошибок компоновки | неограниченно                                                                                                    | ограничено словарём в ~35 операторов      |
| Классы ошибок               | время жизни, владение, потоки, исключения, `Json::Value` и висящие ссылки, забытый `THROW_IF_THREAD_INTERRUPTED` | нет: этих понятий в конфиге не существует |
| Что проверяет компилятор    | типы                                                                                                             | — (схема проверяет больше)                |


Целый пласт правил репозитория относится к ошибкам, которые в декларативной
форме невозможны физически. Это не значит, что правила станут не нужны, —
они останутся для драйверов, но перестанут применяться к autodetect новых
брендов.

### 12.4. Тип задачи, в котором ИИ действительно силён

Задача «прочитай документацию вендора и напиши C++-класс» требует
проектирования: выбрать структуру, распределить ответственность, учесть
время жизни. Задача «прочитай документацию вендора и заполни конфиг» —
это перевод одного структурированного представления в другое. Документация
даёт CGI-путь, имя параметра и формат ответа; конфиг требует ровно их:

```
Документация вендора                     Конфиг
────────────────────────                 ──────────────────────────
GET /stw-cgi/attributes.cgi/             probes:
    attributes/System/Limit/MaxChannel     - id: maxChannel
Ответ: XML, атрибут                          method: GET
       name="MaxChannel" value="4"           path: /stw-cgi/attributes.cgi/...
                                             format: xml
                                         values:
                                           channelCount:
                                             {probe: maxChannel,
                                              xml: {attr: MaxChannel}, as: int}
```

Это отображение почти дословное. Модели ошибаются на проектировании и редко
— на аккуратном переводе, особенно когда результат немедленно проверяется.

### 12.5. Правила из прозы превращаются в валидатор

Часть требований, которые сегодня держатся на дисциплине агента и регулярно
нарушаются, становятся машинно проверяемыми:


| Правило                                                                                            | Сейчас                                                                       | Со схемой                                                                        |
| -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| события autodetect совпадают с событиями рантайма (`cpp-generic-autodetect-event-consistency.mdc`) | текстовое правило, нарушение обнаруживается по молчащим макросам у заказчика | схема сверяет список `events` в конфиге с `.rep`, расхождение — ошибка валидации |
| у детектора с зоной обязаны быть `visualElements`                                                  | нигде не проверяется                                                         | обязательное поле для типов детекторов с геометрией                              |
| нет секретов в репозитории                                                                         | grep вручную                                                                 | схема запрещает литералы в полях учётных данных: только `${credentials.*}`       |
| единый источник детекторов — `.rep`                                                                | по договорённости                                                            | `properties_from_repository` либо явное перечисление, третьего не дано           |


Правило, проверяемое валидатором, не требует, чтобы агент о нём помнил. Это
качественно надёжнее любой формулировки в `.mdc`.

### 12.6. Корпус фикстур можно получить почти даром

Главное возражение против golden-тестов — «кто-то должен записать ответы
устройств». Для существующих вендоров это делается один раз и почти без
ручной работы:

1. На стенде запускается **нынешний** C++-драйвер и выполняется обычный
  autodetect.
2. Снимается HTTP-трафик (прокси или логирование на уровне `syncHttpGet`).
  Каждая пара «запрос → ответ» становится фикстурой.
3. Эталоном становится device description JSON, который драйвер **уже**
  выдаёт: он в логах, строка `Device found:` (например,
   `Drivers/GeneralGeneric/src/AutodetectTool.cpp:567`).

Один прогон на камеру — готовый тест. Побочная польза: тот же корпус
позволяет тестировать сам движок при рефакторинге, чего сейчас нет вообще.

Для **новых** вендоров фикстуры придётся снимать вручную, и это единственная
часть процесса, которую ИИ не делает.

### 12.7. Как выглядит рабочий процесс агента


| Шаг | Кто     | Что происходит                                                                                |
| --- | ------- | --------------------------------------------------------------------------------------------- |
| 1   | человек | снимает фикстуры с камеры на стенде (для нового вендора)                                      |
| 2   | человек | проверяет наличие документации в Lexiro — гейт из `driver-integration-mandatory-workflow.mdc` |
| 3   | агент   | читает документацию, составляет конфиг                                                        |
| 4   | агент   | прогоняет схему и валидатор графа, чинит форму                                                |
| 5   | агент   | прогоняет golden-тест на фикстурах, сравнивает с эталоном                                     |
| 6   | агент   | итерирует до совпадения либо останавливается с формулировкой «не хватает оператора X»         |
| 7   | человек | ревью: сверяет URL и ключи с документацией, принимает решение по недостающим операторам       |


Существенно, что шаги 3–6 — замкнутый цикл без человека и без камеры.
Человек остаётся на входе (документация, фикстуры) и на выходе (ревью
соответствия документации), то есть там, где он незаменим.

### 12.8. Риски и чего это не решает

**Lexiro-гейт не отменяется.** Если документации нет, модель выдумает
CGI-путь в YAML ровно так же уверенно, как выдумала бы его в C++. Схема
удешевляет обнаружение галлюцинации, но не снижает её вероятность.
Единственный настоящий фильтр — golden-тест на реальных ответах, и он
работает только если фикстуры настоящие.

**Риск натягивания на существующие операторы.** Замкнутый словарь провоцирует
агента подогнать задачу под то, что есть, вместо честного «нужен новый
оператор» или «нужен хук». Получится конфиг, который выглядит правдоподобно
и почти работает. Смягчение тройное: golden-тест такой конфиг не пропустит;
в инструкции агента должно быть явно записано, что «остановиться и предложить
оператор» — допустимый и ожидаемый результат; и есть штатный третий вариант —
запросить провайдер значения (8.8), то есть агенту не нужно выбирать между
«натянуть» и «сдаться».

**Риск закрепления существующего бага.** Эталон для миграции — это то, что
нынешний драйвер выдаёт, а не то, что правильно. Если в драйвере есть ошибка,
golden-тест её узаконит. Смягчение: при расхождении конфига с эталоном
проверять по документации, кто из них прав, и фиксировать решение в PR.

**Три вендора не выигрывают ничего.** Honeywell, SIP и GRPC остаются кодом
(раздел 15), и работа с ними по-прежнему требует человека с камерой.

**Схема сама по себе — код, который надо написать и оттестировать.** Выигрыш
появляется не в первом PR, а после того, как ядро и корпус фикстур готовы
(раздел 16).

### 12.9. Ожидаемый эффект, оценочно

Оценки приблизительные, приведены для порядка величин, а не как обязательство.


| Этап интеграции нового бренда | Сейчас                                                                       | Со схемой и фикстурами                            |
| ----------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------- |
| Написать autodetect           | 400–800 строк C++, часы работы человека или агента                           | 60–100 строк конфига, минуты                      |
| Проверить корректность        | стенд с камерой, часы                                                        | golden-тест, секунды                              |
| Итерация после ошибки         | часы (пересборка, деплой, повторный autodetect, повторное добавление камеры) | секунды                                           |
| Ревью                         | чтение C++, сверка с документацией                                           | чтение одного экрана YAML, сверка с документацией |
| Регресс при доработке движка  | не проверяется ничем                                                         | прогон всех фикстур всех вендоров                 |


Последняя строка, возможно, важнее остальных: сегодня изменение общего кода
autodetect нельзя проверить иначе как выборочным тестированием на стенде.

### 13.1. Насколько эта таблица несущая

Две цифры в этой таблице имеют разный статус, и их важно не смешивать.

**Число хуков — 3 из 17 — проверено, а не оценено.** Оно следует из свойств
самого драйвера (транспорт, форма ответа, живое состояние), которые видно в
коде однозначно, поэтому от богатства словаря не зависит. Сплошная проверка в
15.5 подтвердила его целиком, попутно исправив два неверных обобщения:
переживающая autodetect сессия сама по себе хуком не делает, а бинарный обмен
через SDK у Honeywell не сплошной.

**Число «11 покрывается полностью» — гипотеза.** Это оценка достаточности
словаря, и относиться к ней надо соответственно. Она полезна как ориентир
объёма работ, но **предложение на ней не держится**: там, где оператора не
хватило, вместо расширения словаря пишется провайдер значения (8.8) —
небольшая чистая функция, не выводящая участок из-под golden-теста.

Практически это значит, что вердикт «покрывается» в таблице читается как
«покрывается без единой строчки C++», а не как «иначе не заработает». Даже
если реальная цифра окажется, скажем, 8 из 17, оставшиеся вендоры получат по
одному-два провайдера, а не по хуку — число хуков от этого не изменится.
Обоснование такого шва — 11.7, ограничения и бюджет — 8.8 и раздел 14.

### 13.2. Почему Vivotek только частично

Камерная ветка укладывается целиком: рецепты 10.5 и 10.6 закрывают presence-
семантику и кавычки. Ветка NVR — нет. Судя по
`Drivers/VivotekGeneric/src/DriverConstants.h:639-641`, логин устроен так:
открытый текст `"AAA…AAA:<логин>:<пароль>"` дополняется до 159 байт,
шифруется RSA на модуле и экспоненте, полученных из `/fcgi-bin/system.key`,
и отправляется как `encode=<384 hex-символа>`. Описать это можно только
оператором `rsa_encrypt_raw` с управлением паддингом — оператором, который
никогда не понадобится второму вендору.

### 13.3. Почему Luminys только частично

Дело не в недостающем операторе, а в другой модели транспорта.
`Drivers/LuminysGeneric/src/AutodetectTool.cpp:16` поднимает слушающий сокет
на TCP-порту 60005: **устройство подключается к нам само**. Из первого пакета
вытаскивается `<DeviceID type="string">`
(`Drivers/LuminysGeneric/src/DriverHelper.cpp:100-104`), затем по тому же
сокету идёт рукопожатие, выдающее токен `X-cgi-token`, и запускается таймер
поддержания соединения (`AutodetectTool.cpp:21-50`). Это встречный сервер с
сессией на живом сокете, а не запрос. Декларация autodetect такого не
описывает — и не должна. При этом второй, обычный HTTP-режим того же драйвера
описывается конфигом полностью.

### 13.4. Почему Milesight всё-таки покрывается

Каналы (10.8), битовая маска аудиовыхода (10.9), флаги `radarSupport`,
`faceSupport`, `lprSupport` (`Autodetect.cpp:203-221`), реальные модель и
прошивка — всё это обычные значения. Единственная нетривиальная часть —
получение списка событий через ONVIF SOAP
(`Autodetect.cpp:309-321`). Но конверт запроса `GetEventProperties`
статичен, а ответ — обычный XML с деревом топиков. Это честный новый
**транспорт пробы**, а не новый вид логики, поэтому словарь остаётся общим.

## 14. Провайдеры: аварийные выходы в код

Два случая — Hikvision (итерированный salted-хэш в ISAPI-логине) и Vivotek NVR
(RSA с вендорным паддингом) — требуют операторов, полезных ровно одному
вендору. Это признак протечки: замкнутый словарь начинает обрастать
криптографией «под клиента».

**Решение — именованные провайдеры аутентификации.** Конфиг ссылается на
провайдера по имени, реализация живёт в C++:

```yaml
transport:
  auth: provider:vivotek_nvr_rsa
```

Почему это не нарушает декларативность:

- в конфиге нет ни строчки исполняемой логики, только имя;
- это ровно тот же приём, что `properties_from_repository` — ссылка на
способность движка, а не её описание;
- реализация провайдера покрывается обычным юнит-тестом, чего нельзя
сказать о криптографии, размазанной по операторам конфига.

Практический критерий, когда заводить провайдера, а когда — оператор:
**оператор добавляется, если он полезен минимум двум вендорам; иначе это
провайдер.** По этому критерию `count_distinct`, настраиваемые разделители
`kv` и `soap`-транспорт — операторы (нужны нескольким), а `rsa_encrypt_raw`
и `hash_chain` — провайдеры.

### 14.1. Два вида провайдеров и чем они различаются

В схеме два разных аварийных выхода в код, и путать их не следует.

| | Провайдер значения (8.8) | Провайдер аутентификации (этот раздел) |
|---|---|---|
| Что делает | вычисляет значение из тела ответа | проводит логин, выдаёт токен/cookie/заголовок |
| Где объявляется | `values[].provider` | `transport.auth` или `sessions[].provider` |
| Чистая функция | **обязан быть** | по природе не может быть (нонсы, время, сеть) |
| Ходит в сеть | нет, никогда | да, это его работа |
| Покрыт golden-тестом | да, полностью | нет, требует заглушки с записанным токеном |
| Типичный размер | десятки строк | сотня-другая строк |
| Бюджет на вендора | 2–3, больше — это хук | 1 |

Практическое следствие из строки про golden-тест: **провайдер значения
безопасен, провайдер аутентификации — вынужденная мера.** Первый не уменьшает
покрытие тестами, потому что движок по-прежнему прогоняется на фикстурах
целиком. Второй разрывает воспроизводимость на участке логина, и в тестовом
режиме его надо подменять заглушкой, возвращающей заранее записанные
учётные артефакты.

Отсюда правило приоритета при выборе решения для нового вендора:

1. оператор из словаря — если хватает;
2. новый оператор — если он понадобится хотя бы второму вендору;
3. провайдер значения — если вычисление специфично, но данные уже в ответе;
4. провайдер аутентификации — только для логина, только когда без него никак;
5. хук — если сработал чек-лист 11.6.

### 14.2. Чего это не решает

Провайдеры устраняют риск «застряли из-за нехватки оператора», но не
устраняют два других:

- **Провайдеры могут расплодиться.** Если на вендора их пять, конфиг
  превращается в оглавление к C++-коду, и выгода теряется. Отсюда бюджет
  выше и требование фиксировать в PR, почему провайдер не стал оператором.
- **Провайдер аутентификации ослабляет главный приз.** Каждый такой провайдер
  — участок, который golden-тест проверяет через заглушку, то есть слабее.
  Это ещё один довод считать их исключением, а не рядовым инструментом.

## 15. Что остаётся C++-хуком навсегда

**Счёт после сплошной проверки всех семнадцати драйверов (методика и таблица —
в 15.5): хуком остаются 3 драйвера из 17 — Honeywell, SIP и GRPC — плюс одна из
двух веток четвёртого, авторегистрация Luminys. Ещё один участок, логин Vivotek
NVR, требует не хука, а провайдера аутентификации. Расширение схемы на рантайм
(раздел 18) не добавляет к этому счёту ни одного хука.**

Иначе говоря: 11 драйверов из 17 не требуют в autodetect ни строчки C++; ещё у
двух (Hikvision, Vivotek NVR) нужен изолированный провайдер на несколько
десятков строк; у Luminys конфигом покрывается основная HTTP-ветка, а хук нужен
только для авторегистрации; и три драйвера остаются хуком целиком. Сегодня, для
сравнения, конфигом описывается 2 драйвера из 17.

### 15.1. Критерий: autodetect не является обменом «запрос → документ»

Схема из разделов 7–10 устроена по одной оси: сделать HTTP-запрос, разобрать
**тело ответа как документ** (XML, JSON, `key=value`, текст под регулярку),
собрать из полученного значения. Вендор выпадает из схемы, когда его
autodetect не укладывается в эту ось — и это, а не «проприетарность»,
единственный критерий.

Три драйвера выпадают, причём по трём разным причинам:

| Драйвер | Почему выпадает | Что именно не так |
|---|---|---|
| **HoneywellGeneric** | нет документа | обмен идёт через проприетарный SDK: `SdkSession` — обёртка над экспортами `AdproXOaSDK.dll` (`ControlConnectExt`, `GetCamNamesExt`, `GetAllowedCamResolutions`, `GetPTZCapabilities`), а ответ приходит C-структурами и байтовыми векторами с разбором по смещениям (бинарен не весь обмен — уточнение в 15.5) |
| **SIPGeneric** | нет HTTP и не тот выход | транспорт — SIP через `SIPUtils::SIPLibWrapper`; `doAutodetect` возвращает `IpDeviceSearchResult` (бренд, модель, прошивка), а не device description JSON |
| **GRPCGeneric** | autodetect исполняется не здесь | мост: запрос уходит в Go-процесс по gRPC, вся логика бренда живёт на стороне Go |

### 15.2. Насколько «навсегда» в каждом случае

Причины различаются не только по природе, но и по устранимости.

**Honeywell — по-настоящему навсегда.** Гипотетический `transport: sdk`
проблему не решает: экстракторам нечего разбирать. Данные приходят как
`std::vector<SCamNameExt>` и `std::vector<UCHAR>`, разбираемые по фиксированным
смещениям (в коде так и живёт `RESOLUTION_HEADER_SIZE = 6`). Чтобы описать это
декларативно, понадобился бы язык описания бинарных раскладок — ровно то, что
запрещает правило 1 из раздела 7.

**SIP — устранимо, но незачем.** Собственная логика драйвера тривиальна и легла
бы в декларацию целиком: проверить, что устройство отвечает по SIP, и выбрать
модель по бренду — это обычный `map`. Мешает только транспорт и форма выхода.
Добавлять ради этого SIP-транспорт в движок не стоит: выигрыш — три модели и
десяток строк кода.

**GRPC — вопрос не к этому движку.** Брендовая логика там уже вынесена из C++,
и на стороне Go уже применяется декларативный приём (`RequestDescription`,
см. 11.7). Переводить мост в конфиг бессмысленно: конфигурировать нужно то,
что за мостом.

### 15.3. SDK в драйвере ≠ SDK в autodetect

Строку «Honeywell — проприетарный SDK» легко обобщить неверно: будто любой
драйвер, линкующий вендорский SDK, обречён на хук. Это не так — значение имеет
только то, использует ли SDK **сам autodetect**.

Показательный контрпример — `HikvisionGeneric`: он линкует HCNetSDK и SADP
(`Drivers/HikvisionGeneric/CMakeLists.txt:120-259`), но применяет их к поиску и
воспроизведению встроенного архива, обновлению прошивки и сетевому обнаружению
(`RecordingSearchSDK`, `RecordingPlaybackSDK`, `FirmwareUpdater`,
`DeviceSearch`). Autodetect у него — чистый ISAPI поверх HTTP, поэтому в
разделе 13 он в графе «покрывается».

Аналогично Luminys попал в «частично» не из-за SDK, а из-за проприетарного TCP
на порту 60005, где соединение инициирует само устройство (13.3).

### 15.4. Частично покрытые ветки

Плюс две ветки из раздела 13: авторегистрация Luminys и логин Vivotek NVR
(последний — через провайдера аутентификации, то есть код всё же нужен, но
небольшой и изолированный).

### 15.5. Как проверялся счёт

Счёт получен сплошным просмотром autodetect-реализаций всех семнадцати
драйверов по четырём признакам, каждый из которых прямо соответствует одной из
границ схемы:

1. **транспорт** — HTTP/SOAP или что-то иное (критерий 15.1);
2. **форма ответа** — документ (XML / JSON / `key=value` / текст) или бинарные
   структуры (критерий 15.1);
3. **есть ли SET** — меняет ли autodetect конфигурацию устройства (граница 11.3);
4. **переживает ли что-то autodetect** — сокет, процесс, сессия (граница 11.5).


| Драйвер   | Транспорт autodetect | Форма ответа              | Переживает autodetect          | Вердикт     |
| --------- | -------------------- | ------------------------- | ------------------------------ | ----------- |
| NicTech   | HTTP                 | XML                       | —                              | покрывается |
| Hanwha    | HTTP                 | `key=value`, JSON         | —                              | покрывается |
| Panasonic | HTTP                 | текст, `key=value`        | —                              | покрывается |
| Uniview   | HTTP                 | JSON                      | —                              | покрывается |
| Mobotix   | HTTP                 | JSON                      | —                              | покрывается |
| Commax    | HTTP                 | JSON                      | —                              | покрывается |
| IDIS      | HTTP                 | `key=value`               | —                              | покрывается |
| Axis      | HTTP                 | текст, XML                | —                              | покрывается |
| Dahua     | HTTP                 | `key=value`               | —                              | покрывается |
| Milesight | HTTP + ONVIF SOAP    | JSON, SOAP XML            | —                              | покрывается |
| Senturian | HTTP                 | JSON                      | кэш сессии (идемпотентный)     | покрывается |
| Hikvision | HTTP (ISAPI)         | XML                       | кэш сессии (идемпотентный)     | провайдер   |
| Vivotek   | HTTP / FCGI          | `key=value`, JSON         | —                              | провайдер (NVR) |
| Luminys   | HTTP **и** входящий TCP | XML                    | слушающий сокет 60005          | хук (ветка) |
| Honeywell | проприетарный SDK    | C-структуры и байты по смещениям | —                       | **хук**     |
| SIP       | SIP                  | нет тела                  | —                              | **хук**     |
| GRPC      | gRPC в Go-процесс    | protobuf                  | запущенный процесс `GoGrpcServer` | **хук**  |


Из таблицы следуют три факта и два уточнения, каждое из которых исправляет
обобщение, звучавшее в более ранних версиях этого документа.

**Ни один из семнадцати драйверов не делает SET в autodetect.** Граница 11.3
(«пробы не упорядочены, потому что не имеют побочных эффектов») не стоит нам
ничего: она запрещает то, чего никто не делает. Это единственная граница,
проверенная исчерпывающе, а не выборочно.

**Кэш сессии — не состояние в смысле границы 11.5.** Три драйвера удерживают
сессию: Hikvision — в поле самого autodetect-инструмента
(`Drivers/HikvisionGeneric/src/AutodetectTool.h:31`), Senturian — в статическом
слоте на адрес (`Drivers/SenturianServerGeneric/src/Session.cpp:13-23`, тот же
слот берёт `Device.cpp:29`), Vivotek — в локальной переменной `sid`. Во всех
трёх случаях логин идемпотентен и дёшев, повторное выполнение ничего не ломает,
поэтому это оптимизация, а не семантика: декларативный `sessions` (8.1)
покрывает такие случаи целиком. Хуком делает не наличие сессии, а
невозможность её переустановить.

**Настоящее состояние есть ровно у двух драйверов, и оба уже в списке хуков.**
Luminys держит слушающий акцептор на порту 60005 как процессный синглтон, общий
для autodetect, поиска устройств и рантайма
(`Drivers/LuminysGeneric/src/AutoRegReceiver.h:59-67`; берут его
`AutodetectTool.cpp:16`, `DeviceSearch.cpp:13` и `ModuleDriver.cpp:99`). GRPC
запускает Go-процесс (`Drivers/GRPCGeneric/src/AutodetectTool.cpp:191`) и гасит
его в деструкторе.

Уточнение по Luminys, которое легко переврать: рантайм переиспользует **сокет**,
а не токен. Входящее соединение приходит в `Device::handleDevicesInfo`
(`Drivers/LuminysGeneric/src/ModuleDriver.cpp:211-237`), и там устройство
проходит **собственное** рукопожатие через новый `AutoRegProcess`, получая свой
токен (`ModuleDriver.cpp:231-235`). То есть непереводимо здесь именно владение
живым слушающим сокетом, а не переиспользование результатов логина.

Уточнение по Honeywell, работающее в обратную сторону: не весь его SDK-обмен
бинарен. Возможности PTZ приходят как обычный текст `key=value`
(`Drivers/HoneywellGeneric/src/Autodetect.cpp:226-235`) и разбирались бы
экстрактором `kv` без изменений. Хуком драйвер делает другой участок — список
разрешений, который возвращается вектором байт и читается по фиксированным
смещениям (`Autodetect.cpp:144-158`). Достаточно одного такого участка: описать
его нечем, а разрывать autodetect одного устройства между конфигом и кодом
бессмысленно.

## 16. План внедрения

### 16.1. Порядок работ

1. **Починить нынешний движок, не меняя схему.** Три однострочных дефекта:
  выбор ветки по бренду вместо `front()` (5.5), перепутанные лучи и реле в
   `HanwhaDescr` (5.9), удалить или задействовать мёртвые секции (5.6).
   Это полезно независимо от того, будет ли принято остальное.
2. **Собрать корпус фикстур** для уже поддержанных вендоров по процедуре из
  12.6 — снять трафик нынешних драйверов на стенде. Это делается параллельно
   с разработкой ядра и является обязательным условием шагов 3–7: без фикстур
   нечем доказать эквивалентность конфига и хука.
3. **Реализовать ядро новой схемы**: ленивые кэшируемые пробы, значения,
   экстракторы с режимами кардинальности, базовые трансформы и предикаты,
   `assert` из 11.4 и — сразу, а не потом — механизм провайдеров значения
   (8.8). Провайдеры нужны с первого дня именно потому, что снимают риск
   «не хватило оператора» с самого пилота: экзотические операторы можно не
   делать вовсе и посмотреть, какие провайдеры повторяются у разных вендоров.
   На этом этапе проверяются NicTech и Panasonic — самые простые вендоры.
4. **Выпустить JSON-схему и валидатор графа** (уровни 1 и 2 из 12.2) вместе с
  ядром, а не после: без них конфиг нельзя ни проверить в CI, ни доверить
   генерацию ассистенту.
5. **Добавить итерацию и варианты.** Появляются Uniview, Mobotix, Senturian,
  Commax, Axis.
6. **Добавить полное описание детекторов** (мультисобытийность, визуальные
  элементы, чтение `.rep`) и опции модели. Появляются Dahua и Hikvision.
7. **Транспорт SOAP и провайдеры аутентификации.** Появляются Milesight,
  Vivotek, Hikvision-сессия.
8. **Миграция по одному вендору**, каждый — отдельным PR с golden-тестом.

### 16.2. Golden-тесты — главный побочный выигрыш

Сегодня проверить autodetect можно только живой камерой. Замкнутый словарь
делает поведение детерминированным, а значит воспроизводимым офлайн:

1. Один раз записать реальные ответы устройства в фикстуры (файл на пробу).
2. Записать эталонный device description JSON, который выдаёт нынешний
  C++-драйвер на этих же ответах.
3. Тест: «конфиг + фикстуры → JSON» должен побайтово совпасть с эталоном.

Это превращает миграцию из рискованной в механическую: расхождение видно до
того, как код уедет к заказчику. И это же — способ доказать утверждение
«конфиг эквивалентен хуку», которое сейчас проверяется только на глаз.

Как собрать фикстуры почти без ручной работы — см. 12.6; почему именно этот
механизм важнее всего для ИИ-ассистентов — см. 12.2.

### 16.3. Совместимость

Нынешний формат `GeneralGeneric` и новый могут сосуществовать: у них разные
файлы и разные точки входа. Пока новый движок не покрывает вендора, он просто
не используется для него.

## 17. Итог

1. Вывод соседнего документа верен. Нынешний конфиг-движок закрывает 2 бренда
  из 17, полный паритет — только у NicTech. Ограничения — не в разнообразии
   HTTP, а в том, что описание сводится к «URL + ключ + int/bool».
2. Помимо названных в нём причин, движок не умеет описывать зоны детекторов и
  мультисобытийные детекторы, различать каналы, публиковать реальные модель и
   MAC, а также содержит четыре дефекта (5.5–5.9), из которых как минимум один
   делает мультибрендовый конфиг нерабочим.
3. Обойти это декларативно **можно**, не вводя скриптов: нужен переход от
  «списка проб» к «графу именованных шагов с замкнутым словарём операторов»,
   где арифметика, подсчёты, циклы и ветвления выражаются операторами и
   comprehension'ами, а не выражениями и управляющими конструкциями. Часть
   рецептов при этом получается длиннее исходного C++ — почему это ожидаемо и
   когда всё же является сигналом проблемы, разобрано в 10.18.
4. Перевод императивного кода в декларацию механичен, пока «как получить
  значение» — чистая функция от ответа устройства. Не переводятся ровно три
   класса поведения: изменение состояния устройства внутри autodetect, разрыв
   со смыслом «это устройство чужого вендора» и объекты, переживающие
   обнаружение (раздел 11). Второй случай — пробел предложения, а не граница:
   в словарь нужно добавить `assert` (11.4).
5. **Хуком остаются 3 драйвера из 17 — Honeywell, SIP и GRPC — плюс одна из
   двух веток Luminys.** Это результат сплошной проверки по коду (15.5), а не
   оценка: они выпадают потому, что их autodetect не является обменом
   «запрос → документ». Причины у всех трёх разные, «проприетарный SDK» из них
   только у Honeywell (раздел 15), и наличие вендорского SDK в драйвере само по
   себе ни о чём не говорит: у Hikvision он есть, а autodetect всё равно
   описывается конфигом. Остальные 13 драйверов кода в autodetect не требуют
   вовсе либо требуют изолированного провайдера на несколько десятков строк.
6. Эта оценка — гипотеза, и предложение намеренно от неё не зависит (13.1).
   Шов проходит по той же оси, что в React: цель описывается декларативно
   всегда, а вывод значения — декларативно по умолчанию, но с аварийным
   выходом в код через провайдер значения (8.8, обоснование в 11.7). Поэтому
   ошибка в оценке словаря стоит одной небольшой чистой функции, а не
   остановки работы над вендором. Оба существующих в репозитории прецедента —
   `.rep` и `RequestDescription` в Go-стеке — лежат на этой же оси.
7. Единственное место, где замкнутый словарь протекает по-настоящему, —
   вендорная криптография в логине. Её следует выносить в провайдеры
   аутентификации, и это единственный вид провайдера, ослабляющий покрытие
   тестами (14.1).
8. Побочный, но, возможно, главный выигрыш — тестируемость: детерминированный
   движок позволяет проверять autodetect на записанных ответах устройства,
   без камеры на столе.
9. Из тестируемости следует главный аргумент в пользу схемы при внедрении ИИ
   (раздел 12): сегодня ассистент не может проверить написанный им autodetect
   иначе как через человека с камерой, а схема замыкает цикл «сгенерировал →
   проверил → поправил» на секунды. Дополнительно часть требований, которые
   сейчас держатся на дисциплине агента, становится машинно проверяемой.
   При этом Lexiro-гейт не отменяется: без документации модель выдумает
   CGI-путь в YAML так же уверенно, как в C++.
10. Наконец, о масштабе — чтобы предложению не приписали лишнего. Autodetect
   составляет 2–7% кода Generic-драйвера (замеры в 11.8), поэтому это не «шаг
   к zero code»: код не исчезает, а переезжает из семнадцати драйверов в один
   движок. Настоящий «бренд без кода» потребовал бы декларативного рантайма.
11. Рантайм при этом не является чужой территорией. Раздел 18 показывает, что
   конфигурирование детекторов, применение настроек и разбор событий ложатся на
   тот же словарь плюс пять конструкций (`inputs`, `property_map`, `handlers`,
   `event_sources`/`event_parsers`, `geometry`), а в Go-стеке нужный шов уже
   проведён: `PrepareApplySettings`, `OnStart` и подписка возвращают описания
   запросов, а `ParseEvents` — чистая функция от payload. Хуками остаются только
   удержание соединения, реконнект и двухфазный автомат события. Начинать стоит
   с разбора событий: чистая функция, дешёвые фикстуры, наибольшая цена ошибки.

## 18. Расширение схемы на рантайм: детекторы, события, настройки

Всё предыдущее относилось к autodetect. Этот раздел отвечает на следующий
естественный вопрос: ложатся ли на ту же схему остальные подсистемы —
конфигурирование детекторов аналитики, получение событий и чтение/запись
настроек. Короткий ответ: ложатся, причём без хуков почти целиком, и это не
новая архитектура, а перевод уже существующего разделения в конфиг.

### 18.1. Шов уже проведён — в Go-стеке

Ключевое наблюдение: интерфейс `IVideoAnalytics`
(`Go/GrpcServer/interfaces/interfaces.go:106-112`) состоит из методов, которые
**ничего не исполняют**:

- `PrepareApplySettings`, `OnStart`, `OnStop` возвращают списки
  `RequestDescription` — что послать, а не как
  (`Go/GrpcServer/brands/GIT/analytics/motionDetection.go:94-140`).
- `ParseEvents` получает тело `req.Data` и возвращает список событий — чистая
  функция от полезной нагрузки
  (`Go/GrpcServer/brands/tiandy/analytics/baseDetector.go:46-75`).
- Даже подписка на поток описана **данными**: `ReceiverDescription` с вложенным
  `HttpStreamReceiver` и флагом `restart`
  (`Go/GrpcServer/brands/homaxi/analytics/httpStreamReceiver.go:15-45`).
  Держит соединение, переподключается и режет поток на сообщения C++-хост.

То есть «что» и «кто исполняет» в этих подсистемах уже разделены, и брендовый
Go-код — это ровно то, что должно стать конфигом. Задача сводится к размеру
словаря, а не к наличию принципиальной границы.

### 18.2. Что добавляется к словарю

Autodetect — однократное «прочитать и выдать документ». Рантайм — набор
**обработчиков**, которые хост вызывает многократно с аргументами. Отсюда пять
новых конструкций (три правила раздела 7 при этом не нарушаются: ни выражений,
ни управляющих конструкций, словарь остаётся замкнутым).

| Конструкция | Зачем |
|---|---|
| `inputs` | пространство аргументов обработчика: настройки, зоны, канал, поток, payload. Играет ту же роль, что `probes` в autodetect — источник значений |
| `property_map` | таблица «свойство из `.rep` ↔ параметр вендора»; закрывает бо́льшую часть applySettings одной декларацией |
| `handlers` / `emit` | именованные точки входа (`on_start`, `on_stop`, `apply_settings`, `set_relay`), каждая — чистая функция аргументов в список запросов |
| `event_sources` / `event_parsers` | описание подписки и разбор payload в события |
| `geometry` | семейство трансформов для зон: нормализованные координаты в вендорский формат |

Плюс один примитив для записи настроек — `read_modify_write` (обоснование в
18.4).

### 18.3. Скелет расширенной схемы

```yaml
# ─── общая часть, как в autodetect ────────────────────────────────
transport: {scheme: http, port: 80, auth: digest}
sessions:  [...]
probes:    [...]          # ленивые, кэшируемые в пределах вызова
values:    {...}          # именованные чистые значения

# ─── таблица свойств: продукт ↔ вендор ────────────────────────────
property_map:
  - {id: enabled,     param: VID_MOTIONENABLE, map: {true: 2, false: 0}}
  - {id: sensitivity, param: "ETC_MDTHRESHOLDS${index}",
     index: {range: {from: 1, to: 8}}, as: int}

# ─── обработчики: аргументы → запросы ─────────────────────────────
handlers:
  detector.motion.on_start:
    emit:
      - {method: GET, path: /cgi-bin/param.cgi, query: {VID_MOTIONENABLE: 2}}
      - {method: GET, path: /cgi-bin/param.cgi, query_from: {ref: values.defaultSchedule}}

  detector.motion.on_stop:
    emit:
      - {method: GET, path: /cgi-bin/param.cgi, query: {VID_MOTIONENABLE: 0}}

  detector.motion.apply_settings:
    emit:
      - {method: GET, path: /cgi-bin/param.cgi, query_from_property_map: true}
      - method: GET
        path: /cgi-bin/param.cgi

          VID_MOTIONREGION:

              source: {ref: inputs.visual_elements}
              kind: rect

              round: nearest
              corners: absolute

              join: ""
              pad: {to: 64, with: "00", truncate: true}

  videoSource.apply_settings:
    read_modify_write:
      read:   {probe: videoEncodeCache}
      locate: {json: {path: "data.streamEncode[streamType=${inputs.stream}]"}}
      apply:  {from_property_map: true}
      write:
        method: POST
        path: /api/video/video-encode
        body: {json_document: whole}         # шлём документ целиком

# ─── подписка на поток событий ────────────────────────────────────
event_sources:
  - id: alerts
    receiver: http_stream        # http_stream | long_poll | onvif_pullpoint | rtsp_metadata
    request:
      method: POST
      path: /api/event
      body: {template: '{"method":"set.event.subscribe","content":${subscribers}}'}
    subscribers:                 # тело собирается из активных детекторов
      for_each: {ref: runtime.active_detectors}
      map: {motionDetection: VMD, lineCrossing: TRIPWIRE}
      unique: true
    framing: {split: json_object}
    restart: {when: {status: {ne: 200}}}

# ─── разбор событий: payload → события ────────────────────────────
event_parsers:
  - id: alerts
    source: alerts
    select:  {xml: {path: AlertStateList.AlertState}, mode: all}
    channel: {xml: {path: channelID}, as: int, sub: 1}
    match:   {xml: {path: eventType}}
    state:   {xml: {path: eventState}, map: {active: true, inactive: false}}
    timestamp: engine_clock      # либо {xml: {path: dateTime}, format: iso8601}
    events:
      - {when: {match: {eq: VMD}},      id: motionDetection, type: two_phase}
      - {when: {match: {eq: TRIPWIRE}}, id: lineCrossing,    type: two_phase}
```

### 18.4. Три решения, которые стоит зафиксировать

**Геометрия — оператор, а не провайдер.** Кодирование зоны выглядит как код
только потому, что для него нет словаря. На самом деле это одна и та же
фиксированная цепочка шагов, у которой от вендора к вендору меняются параметры.

Было — `Go/GrpcServer/brands/GIT/analytics/motionDetection.go:42-70`:
нормализованный прямоугольник умножается на сетку 23×15, каждая координата
пакуется в `%02X`, зоны склеиваются, результат добивается нулями до 64 символов
и обрезается:

```go
for _, elem := range visualElements {
    if rect := elem.GetRect(); rect != nil {
        x1 := int(math.Round(rect.Left * GRIDMAP_WIDTH))
        y1 := int(math.Round(rect.Top * GRIDMAP_HEIGHT))
        x2 := x1 + int(math.Round(rect.Width*GRIDMAP_WIDTH))
        y2 := y1 + int(math.Round(rect.Height*GRIDMAP_HEIGHT))
        coords := fmt.Sprintf("%02X%02X%02X%02X", uint8(x1), uint8(y1), uint8(x2), uint8(y2))
        builder.WriteString(coords)
    }
}
for builder.Len() < 64 {
    builder.WriteString("00")
}
allCoords = builder.String()
if len(allCoords) > 64 {
    allCoords = allCoords[:64]
}
urlBuilder.AddParam("VID_MOTIONREGION", allCoords)
```

Стало:

```yaml
values:
  motionRegion:
    geometry:
      source: {ref: inputs.visual_elements}
      kind: rect                              # берём только прямоугольники
      scale: {x: 23, y: 15}                   # 0..1 → сетка вендора
      round: nearest
      corners: absolute                       # x2,y2 = точки, а не ширина/высота
      encode: {as: hex, width: 2, uppercase: true, order: [x1, y1, x2, y2]}
      join: ""                                # зоны идут подряд, без разделителя
      pad: {to: 64, with: "00", truncate: true}

handlers:
  detector.motion.apply_settings:
    emit:
      - method: GET
        path: /cgi-bin/param.cgi
        query: {VID_MOTIONREGION: {ref: values.motionRegion}}
```

Каждая строка `geometry` соответствует одному шагу оригинала, и все различия
между вендорами — это её параметры, а не другая логика:

| Шаг | Ключ | Что варьируется у вендоров |
|---|---|---|
| выбор фигур | `kind` | `rect`, `polyline`, `polygon`, `grid_mask` |
| перевод в систему координат вендора | `scale` | сетка 23×15, 32×32, проценты, 0..1000, пиксели кадра |
| округление | `round` | `nearest`, `floor`, `ceil` |
| форма записи угла | `corners` | абсолютные координаты против «левый верх + ширина/высота» |
| кодирование | `encode` | hex-байты, десятичные числа, битовая маска ячеек |
| склейка зон | `join` | пусто, `,`, `;`, отдельный параметр на зону (`index`) |
| выравнивание длины | `pad` | фиксированные 64 символа, отсутствие паддинга, дополнение до числа ячеек |

Из этой таблицы и следует вывод: цепочка одна, параметры разные — значит,
критерий раздела 14 («полезно минимум двум вендорам») выполняется и место в
словаре оправдано. Экзотические упаковки, которые не выражаются этими шагами
(например, зона как RLE-битмап или как проприетарный бинарный блок), остаются
провайдером значения (8.8) — но провайдером становится именно кодирование, а не
весь `apply_settings`.

**`read_modify_write` — второе и последнее упорядоченное место в схеме.**
Правило `go-grpc-set-body-completeness.mdc` требует не собирать тело SET с
нуля, а взять закэшированный ответ GET и подменить в нём затронутые поля —
иначе прошивка либо отвергает запрос, либо затирает настройки оператора. Это
вводит порядок, который 11.3 запрещает для `probes`. Разрешать его следует так
же, как уже разрешён порядок внутри `sessions.steps`: одним именованным
примитивом с фиксированной семантикой, а не общей упорядоченностью проб.

**Часы объявляются, а не берутся.** В
`Go/GrpcServer/brands/tiandy/analytics/baseDetector.go:55` время события берётся
из `time.Now().UnixMilli()` — нечистота, из-за которой golden-тест
невоспроизводим. В схеме `timestamp` либо извлекается из payload, либо явно
помечается `engine_clock`, и тогда в тестовом режиме движок подставляет
фиксированное время.

### 18.5. Что покрывается без хуков, а что нет


| Участок | Вердикт |
| ------------------------------------------------------------ | ------------------------------------------------------ |
| Чтение конфигурации устройства                                | словарь autodetect без изменений                       |
| Запись настроек по таблице свойств                            | `property_map` + `emit`                                |
| Полное тело SET из кэша GET                                   | `read_modify_write`                                    |
| Старт/стоп детектора, расписания                              | `emit`                                                 |
| Зоны: прямоугольники, полигоны, сетки, hex/CSV                | `geometry`                                             |
| Подписка HTTP-stream, long-poll, ONVIF pull-point             | `event_sources`                                        |
| Разбор XML/JSON-событий, фильтр по каналу, маппинг типов      | `event_parsers`                                        |
| Свойства детектора для UI                                     | уже есть — `.rep` и `properties_from_repository`       |
| Двухфазный автомат, дедупликация, таймауты                    | движок; конфиг объявляет `type` и `dedup_by`           |
| Реконнект и бэкофф подписки                                   | движок                                                 |

**Расширение на рантайм не добавляет ни одного нового хука.** Единственная
строка с вердиктом «хук» — это уже известная граница 11.3, а не новый случай:
две строки над ней уходят в провайдеры, всё остальное покрывается словарём или
движком. Счёт из раздела 15 (3 драйвера из 17 плюс ветка Luminys) остаётся в
силе и после расширения.

### 18.6. Что это даёт проверяемости

Здесь выигрыш больше, чем в autodetect. Golden-тест обобщается до
«(обработчик, аргументы, ответы проб) → ожидаемые запросы», то есть можно
утверждать точный URL и точное тело, которое уйдёт в камеру. Сегодня это не
проверяется ничем. Для событий фикстура ещё дешевле: записанный payload и
ожидаемый список событий.

Появляется и перекрёстная проверка, которой сейчас не существует в принципе:
если autodetect и `event_parsers` лежат в одном конфиге, движок сам сверит
множество объявленных идентификаторов событий с множеством порождаемых. Это
ровно то, что сегодня удерживается дисциплиной через
`cpp-generic-autodetect-event-consistency.mdc` и ломается молча — детектор
объявляет одни id, рантайм поднимает другие, макросы у заказчика не
срабатывают, а логи выглядят здоровыми.

### 18.7. Порядок расширения

1. **Разбор событий.** Наибольшая ценность при наименьших затратах: чистая
   функция, дешёвые фикстуры (пачка payload'ов с одной камеры), максимальная
   цена ошибки (не сработавшая тревога), нулевое текущее покрытие тестами.
2. **Чтение конфигурации.** Почти даром — тот же словарь, что у autodetect.
3. **Запись настроек.** Нужны `property_map`, шаблоны тела и
   `read_modify_write`.
4. **Геометрия зон.** В последнюю очередь и сначала через провайдеры: операторы
   в словарь добавлять после того, как станет видно, какие шаги повторяются у
   нескольких вендоров.

Оценка объёма по двум реально прочитанным файлам (прикидка, не замер):
обработчик motion у GIT — около 120 строк Go против примерно 25 строк такого
конфига; `ParseEvents` у tiandy — 30 строк против примерно 12.

```powershell
  $all = (Get-ChildItem "Drivers\$d\src" -Include *.cpp,*.h -Recurse | Get-Content | Measure-Object -Line).Lines
  $ad  = (Get-ChildItem "Drivers\$d\src" -Include Autodetect*.cpp,Autodetect*.h -Recurse | Get-Content | Measure-Object -Line).Lines
  "{0,-18} total={1,6}  autodetect={2,5}  {3,5:N1}%" -f $d,$all,$ad,(100*$ad/$all)
}
```

Замер намеренно грубый: считаются только файлы с именем `Autodetect*`, поэтому
вспомогательный код, используемый и autodetect, и рантаймом (например
`DetectWindowHelper` у Dahua или `Device::getChannelsCount`), в долю не попал.
Реальная доля чуть выше, но порядок величины тот же.
